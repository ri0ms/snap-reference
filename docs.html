Part 1

제품 요구사항 (PRD)

무엇을 왜 만드는가. 완료 기준까지.

01

개요

지금은 각자 마음에 드는 사진과 링크를 개인 폴더, 카카오톡 대화방, 핀터레스트 보드에 제각각 모읍니다.

  • 상대방이 무엇을 모았는지 그때그때 볼 수 없습니다.
  • 대화방에 올린 이미지는 시간이 지나면 위로 밀려서 다시 찾기 어렵습니다.
  • "이거 어때?" 같은 의견이 이미지와 따로 놀아, 나중에 보면 무슨 이야기였는지 모릅니다.

Reference는 모으는 곳 = 보는 곳 = 이야기하는 곳을 하나로 합칩니다.

1-1무엇을 모으는가 — 스냅사진 레퍼런스

이 보드는 촬영 컨셉을 정하기 위한 스냅사진 참고 이미지를 모읍니다. 그래서 분류 기준을 "아무 이름이나 붙이는 폴더"가 아니라 실제 촬영 종류 6가지로 처음부터 고정했습니다. 고를 필요 없이 이미 나뉘어 있어야 저장이 빨라지기 때문입니다.

보드
├── 1. 개인          ← 카테고리 6개, 고정 (추가·삭제 없음)
├── 2. 커플
├── 3. 친구·우정
├── 4. 일상스냅
├── 5. 셀프웨딩
└── 6. 웨딩스튜디오
        └── 야외 / 실내 / 필름톤 …   ← 폴더, 사용자가 생성 (1단계까지만)
  • 카테고리는 6개 고정. 이미지 1장은 카테고리 1개에만 속합니다.
  • 폴더는 카테고리 안에서 사용자가 만듭니다. 이미지 1장은 폴더 0~1개에 속합니다.
  • 폴더 안에 폴더는 만들 수 없습니다.

대상 사용자

주 사용자는 2~5명 규모의 친한 그룹 하나입니다. 가정

Persona A · 보드를 만든 사람
지훈 (26)
상황
친구와 촬영 컨셉을 잡는 중. 인스타그램·핀터레스트·블로그를 돌며 하루 10~20장을 발견한다.
원하는 것

불편한 점

Persona B · 초대받은 사람
수아 (27)
상황

원하는 것
링크 하나 눌러 바로 들어가, 지훈이 뭘 올렸는지 훑고 "이건 좀 아닌 듯" 한마디 남기고 싶다.

03

해결할 문제

3-1문제 상황

  • 실시간성 없음 — 물어보기 전엔 친구가 뭘 모았는지 알 수 없다.
  • 정리 안 됨 — 대화방 이미지는 시간순으로만 쌓여 컨셉별로 다시 볼 수 없다.
  • 링크가 안 보임 — 링크만 공유하면 파란 글씨 하나뿐이라, 열어보기 전엔 뭔지 모른다.
  • 의견이 흩어짐 — 이미지는 A에, 그에 대한 반응은 B에 남는다.

3-2지금은 어떻게 해결하고 있나

현재 방법되는 것안 되는 것
카카오톡 단톡방즉시 공유, 알림시간순뿐 · 검색/분류 불가 · 이미지 만료
각자 PC 폴더정리 잘 됨상대방이 볼 수 없음
핀터레스트 공유 보드이미지 정리외부 이미지·링크 넣기 번거로움, 가입 필요
구글 드라이브파일 공유썸네일 보기 불편, 댓글이 이미지와 안 붙음
빈칸: "즉시 공유 + 컨셉별 정리 + 이미지와 링크 모두 + 그 자리에서 댓글"을 한 번에 해주는 도구가 없습니다.
04

사용자 흐름

흐름 A보드 만들고 초대하기 · 최초 1회

A-1
보는 화면첫 화면 — "보드 만들기" 버튼 하나
하는 행동버튼 클릭
A-2
보는 화면이름 입력 창 — 닉네임만, 비밀번호 없음 가정
하는 행동닉네임 입력 후 시작
A-3
보는 화면빈 보드 + "초대 링크 복사" 버튼
하는 행동링크 복사해 카톡으로 친구에게 전달
A-4
보는 화면(친구 화면) 링크를 열면 닉네임 입력 창
하는 행동닉네임 입력 후 같은 보드에 입장

흐름 B카테고리 고르기 · 모든 작업의 출발점 NEW

B-1
보는 화면보드 홈 — 큰 제목 SNAP REFERENCE + [총 342장]
하는 행동훑어봄
B-2
보는 화면그 아래 6개 카테고리 카드가 한 줄로 배열. 각 카드는 대표 사진 1장 + 이름 + [장수]
하는 행동원하는 컨셉 선택 — 예: "셀프웨딩"
B-3
보는 화면새 사진이 올라온 카테고리는 이름 옆에 파란 점
하는 행동점이 있는 카드를 우선 확인
B-4
보는 화면카테고리 상세 — 사진 그리드 + 폴더 칩 + 사진 올리기
하는 행동여기서 흐름 C·D·E·F로 이어짐

흐름 C이미지 올리기 · 핵심 흐름

C-1
보는 화면카테고리 상세 화면 — 예: "셀프웨딩 [52]"
하는 행동(선택) 넣을 폴더 칩을 먼저 클릭
C-2
보는 화면화면 아무 곳
하는 행동이미지 파일을 드래그해 놓기 (또는 ↑ 사진 올리기)
C-3
보는 화면전체 화면 안내 — "여기에 놓으면 [셀프웨딩 · 야외]에 올라갑니다"
하는 행동놓기
C-4
보는 화면그리드 맨 앞에 자리가 먼저 생기고 진행 바 → 완료되면 사진으로 바뀜
하는 행동확인
C-5
보는 화면사진에 올린 사람 닉네임·시간 (마우스를 올리면 보임)
하는 행동— 여기서 "행위 완료"
C-3의 문구에 카테고리와 폴더 이름을 박아 넣는 것이 이 흐름의 핵심입니다. 어디에 올라가는지 놓기 전에 알려주면, 잘못 올려놓고 다시 옮기는 일이 없어집니다.

흐름 D링크 올리기

D-1
보는 화면카테고리 상세 화면
하는 행동URL 붙여넣기 (Ctrl+V) 또는 링크 입력창에 Enter
D-2
보는 화면제목·설명·대표 이미지를 자동으로 불러온 카드 — OG 태그(웹페이지가 공유용으로 미리 넣어둔 대표 이미지·제목 정보)를 읽어옴
하는 행동확인
D-3
보는 화면추출 실패 시 — 기본 카드 + "이미지 직접 넣기"
하는 행동그대로 저장하거나 이미지 직접 첨부

흐름 E보고, 말하고, 받기

E-1
보는 화면친구가 방금 올린 사진이 파란 테두리로 4초간 표시됨
하는 행동사진 클릭
E-2
보는 화면상세 보기 — 원본 크게 + 오른쪽에 업로더·폴더·댓글 + 다운로드
하는 행동댓글 입력 "이거 좋다"
E-3
보는 화면댓글이 오른쪽 패널에 즉시 표시
하는 행동← → 키로 다음 사진 확인
E-4
보는 화면다운로드 버튼
하는 행동클릭 → 원본 이미지가 기기에 저장됨

흐름 F카테고리 안에서 폴더로 다시 나누기 NEW

F-1
보는 화면카테고리 상세 상단의 폴더 칩 행 — 전체 / + 폴더
하는 행동+ 폴더 클릭
F-2
보는 화면그 자리에 바로 입력창이 열림
하는 행동폴더 이름 입력 — 예: "야외", "필름톤" → Enter
F-3
보는 화면칩 행에 새 폴더가 추가됨
하는 행동분류할 사진들을 체크 (또는 드래그로 여러 장 선택)
F-4
보는 화면하단 액션 바 — 12장 선택 · 폴더로 이동 · 다운로드 · 삭제
하는 행동"폴더로 이동" → 폴더 선택
F-5
보는 화면폴더 칩
하는 행동클릭 → 해당 폴더 사진만 표시 (전체로 되돌릴 수 있음)
폴더와 카테고리의 차이 (확정) — 카테고리는 6개로 미리 정해진 촬영 종류이며 바꿀 수 없습니다. 폴더는 그 안에서 사용자가 직접 만드는 하위 분류입니다. 예: 셀프웨딩 > 야외. 한 사진은 카테고리 1개, 폴더 0~1개에 속합니다.

8-2결정해주셔야 할 질문

  1. "실시간"의 기준을 어디까지로 잡을까요?① 새로고침하면 보임(개발 빠름) / ② 자동으로 화면에 나타남(개발 기간 +약 3~5일 가정). 원래 말씀하신 문제가 "실시간 확인 불가"였기 때문에, 이 답에 따라 제품의 체감이 크게 달라집니다.
  2. 링크는 주로 어떤 사이트에서 가져오시나요?인스타그램·핀터레스트는 이미지 추출이 자주 막힙니다. 실제로 쓰실 사이트 3~5곳을 알려주시면 그곳부터 확실히 되게 만들겠습니다.
  3. 친구 외에 다른 사람이 링크를 알게 되면 어떤가요?① 링크만 알면 누구나 입장(간편, 노출 위험) / ② 4자리 입장 코드 추가(한 단계 더 번거로움).
  4. 폴더와 카테고리, 둘 다 꼭 필요한가요?v0.2에서 해결됨 — 카테고리 6개 고정 + 그 안의 폴더로 확정.
  5. 다운로드가 정말 자주 쓰이나요?보기만 하면 되는지, 실제로 파일을 내려받아 다른 곳에 쓰시는지에 따라 원본 보관 방식과 저장 용량 설계가 달라집니다.
  6. 카테고리 대표 이미지를 직접 고르고 싶으신가요?지금은 "가장 최근에 올린 1장"이 자동으로 올라옵니다. 보드 첫 화면의 인상이 매번 바뀌는 셈인데, 마음에 드는 한 장을 고정하는 방식이 더 나을 수도 있습니다.
  7. "친구·우정" 이라는 이름 그대로 갈까요?카드 폭이 좁아 두 단어가 한 줄에 들어가려면 글자가 작아집니다. "우정" 한 단어로 줄이면 나머지 5개와 글자 크기가 맞습니다.
MAKER

Review

①가장 약한 부분

6개 카테고리가 실제 사진 분포와 맞는다는 근거가 없습니다. 이 문서와 디자인 전체가 "6개로 나뉜다"를 전제로 지어져 있습니다 — 보드 홈 한 줄 배치, 카드 폭, 고정 카테고리, 폴더의 위치까지 전부 여기에 매여 있습니다. 그런데 실제로는 일상스냅 한 곳에 70%가 쏠리고 웨딩스튜디오는 3장뿐일 수 있습니다. 그러면 홈 화면의 6칸 중 절반이 늘 비어 보이고, 정작 사진이 몰린 카테고리는 폴더 없이 감당이 안 됩니다.

이 가정은 코드 없이 30분이면 검증됩니다: 지금 각자 가지고 있는 레퍼런스 사진 30~50장을 6개 이름으로 직접 나눠보면 됩니다. v0.1에서 지적했던 "Must가 많다"는 문제는 계층이 확정되며 정리됐지만, 그 계층 자체의 근거는 아직 비어 있습니다.

부차적으로, Must 기능이 20개로 늘었습니다(v0.1은 14개). 1개월 일정과 맞는지는 개발자 산정이 필요합니다. 확인 필요

②개발자·디자이너가 반드시 물어볼 질문

Q1. "실시간이라고 써 있는데, 웹소켓인가요 폴링인가요? 아니면 그냥 새로고침인가요?"

AMVP는 새로고침 기준입니다(Must). 자동 갱신은 Nice로 분리했고, 만든다면 웹소켓보다 3~5초 주기 폴링을 권합니다 — 인원이 5명 이하라 서버 부담이 거의 없고 구현이 훨씬 단순합니다. 다만 처음 호소한 문제가 "실시간 확인 불가"였으므로, 질문 1번의 답에 따라 Must로 올라갈 수 있습니다.

Q2. "저스티파이드 그리드면 이미지 원본 비율을 언제 알죠? 받아봐야 아는 구조면 첫 렌더에서 레이아웃이 튑니다."

A업로드 시점에 서버가 비율을 저장합니다. 클라이언트는 목록 API에서 ratio를 함께 받아 행 배치를 먼저 계산하므로, 이미지가 도착하기 전에 자리가 잡힙니다(CLS 0). 업로드 중인 사진도 파일에서 즉시 비율을 읽어 자리를 먼저 만듭니다.

Q3. "닉네임만으로 들어오면 같은 사람인지 어떻게 구분하죠?"

A브라우저 저장소에 닉네임과 임시 식별자를 저장해, 같은 기기·같은 브라우저라면 다시 묻지 않습니다. 다만 다른 기기에서 접속하면 다른 사람으로 인식됩니다(본인 사진 삭제 권한에 영향). 확인 필요

Part 2

디자인 명세

어떻게 보이고 어떻게 움직이는가. 레퍼런스 2장(사진작가 포트폴리오형 미니멀 에디토리얼)을 기준으로 잡았습니다.

D1

디자인 원칙 5가지

이 사이트는 스냅사진 레퍼런스를 모으는 곳입니다. 화면이 예뻐 보이는 것보다 올린 사진의 색·톤·분위기를 정확하게 판단할 수 있는 것이 먼저입니다.

  1. 색은 사진만 쓴다. UI는 무채색으로 고정합니다. 배경·버튼·라벨에 색이 들어가면 사진의 색 판단이 틀어집니다. 유일한 예외는 "실시간 신호"용 블루 한 가지입니다.
  2. 테두리보다 여백. 카드 박스, 그림자, 둥근 모서리를 쓰지 않습니다. 사진은 직각 그대로, 구분은 여백과 1px 실선으로만 합니다.
  3. 글자는 작고 얇게, 제목만 크게. 본문·라벨은 11~14px로 조용히, 페이지 제목만 과감하게 큽니다. 레퍼런스의 대비 구조입니다.
  4. 사진 비율을 자르지 않는다. 스냅 레퍼런스는 프레이밍 자체가 참고 대상입니다.
  5. 한 화면에 정보를 겹쳐 얹지 않는다. 사진 위에 텍스트를 올리지 않고 항상 사진 바깥 아래에 둡니다. (유일한 예외: 마우스를 올렸을 때의 업로더 정보)

D5-1저스티파이드 그리드

레퍼런스 2번은 메이슨리(세로 벽돌쌓기)가 아닙니다. 한 행 안에서 사진들의 높이가 같고 폭이 제각각입니다. 같은 방식으로 만듭니다.

속성값
방식행 단위 저스티파이드 — 각 사진 폭 = 높이 × 원본비율, 행 합계가 컨테이너 폭이 되도록 높이를 미세 조정
목표 행 높이데스크톱 260px (허용 200~330px)
사진 간격18px (가로·세로 동일)
마지막 행남는 칸을 늘려 채우지 않고 왼쪽 정렬로 그대로 둠 — 억지로 늘리면 마지막 사진만 비정상적으로 커짐
자르기없음. 원본 비율 유지
정렬최신순 고정
왜 메이슨리가 아닌가 — 메이슨리는 세로로 읽히고, 스크롤할 때 사진들이 서로 다른 위치에서 튀어나옵니다. 저스티파이드 그리드는 행 단위로 눈이 끊기기 때문에 여러 장을 나란히 비교하기 쉽습니다. 레퍼런스 비교가 목적인 이 제품에 맞습니다.

D8-2저스티파이드 그리드 계산

// photos: [{ id, ratio }]   ratio = 원본 width / height
function layoutRows(photos, containerW, targetH, gap) {
  const rows = []; let row = [], sumRatio = 0;
  for (const p of photos) {
    row.push(p); sumRatio += p.ratio;
    // 이 행을 컨테이너 폭에 맞췄을 때의 실제 높이
    const h = (containerW - gap * (row.length - 1)) / sumRatio;
    if (h <= targetH) { rows.push({ items: row, height: h }); row = []; sumRatio = 0; }
  }
  // 마지막 행은 늘리지 않고 targetH 그대로 왼쪽 정렬
  if (row.length) rows.push({ items: row, height: targetH, last: true });
  return rows;
}
  • 원본 비율은 업로드 시점에 서버에 저장합니다. 이미지를 받아봐야 비율을 아는 구조면 첫 렌더에서 레이아웃이 튑니다.
  • 썸네일은 목표 행 높이의 2배(520px 높이)로 생성해 고해상도 화면까지 커버합니다.

D8-4다음에 결정할 디자인 사항

  1. 보드 홈 히어로 문구SNAP REFERENCE로 제안했습니다. 다른 문구를 원하시면 영문 대문자 12~16자가 레퍼런스 비율에 맞습니다.
  2. 카테고리 대표 이미지자동(최신 1장)으로 잡았습니다. 직접 고르는 방식이 필요한지 확인이 필요합니다.
  3. 6개 카테고리 순서요청하신 순서를 고정으로 두었습니다. 사진이 많은 순으로 자동 정렬하는 방식도 가능합니다.
  4. "친구·우정" 표기카드 폭에 두 단어가 들어가야 해 가운뎃점으로 묶었습니다. "우정"만 쓰는 편이 짧고 읽기 쉽습니다.
이 PRD에서 가장 먼저 검증해야 할 것 1가지

지금 가진 레퍼런스 사진 30장을 6개 카테고리로 나눴을 때, 한 곳에 몰리지 않고 실제로 갈라지는가.

이 6개 구분 위에 홈 화면·업로드 흐름·폴더 위치까지 전부 올라가 있는데, 아직 사진 한 장으로도 확인된 적이 없습니다. 코드 없이 30분이면 끝납니다.

함께 진행할 1일차 기술 확인 — 인스타그램·핀터레스트 URL 10개로 OG 태그 추출을 돌려봅니다. 이것이 안 되면 링크 카드가 전부 회색 빈 박스가 되어, 이 제품은 카톡보다 나을 게 없어집니다.
